# 再生シナリオとテスト

ユーザー操作から期待結果を定め、本体の回帰を検証するための Gherkin シナリオです。
**178定義のうち、自動テスト実装あり173、今回の対象外4、実機確認待ち1です。実装ありと合格済みは区別します。**

確定した仕様は [DECISIONS.md](DECISIONS.md)。状態と操作の対応、重複整理は [点検結果](AUDIT.md)、設計IDとテストの対応は [実装対応表](IMPLEMENTATION.md)、実行範囲と結果は [検証記録](RESULTS.md) を参照してください。
既存の `spec/features` は実行対象として維持し、このディレクトリは現在の
`scenarios("../../features/frontend")` / backend / integration の収集対象外に置いています。
実行可能な例は features 配下のGherkinと step_defs 配下のパラメータ化テストに具体化し、観測手段とともに実装しています。
元の設計IDとの対応を記録し、部分実装を設計全体の完了と扱わないでください。
`@planned` タグ自体に自動スキップ機能はありません。

既存のシナリオと重なるものもあります。これは新規テストだけの一覧ではなく、
既存テストで本当に検証できているかを見直すための一覧でもあります。
移行時は既存シナリオを拡充できるか確認し、同じ内容の重複を増やさないでください。

## タグと識別子

- `@reported`: 報告された3回目の再生停止と、不正解後のロード停止の再現・復帰。
- `@p0`: 通常進行の停止、誤音源、意図しない音声、二重加点につながる優先ケース。
- `@p1`: その他の境界、操作性、環境差、長時間進行。
- `@decision_resolved`: ユーザーの回答を反映し、具体的な期待結果を確定したケース。
- `@out_of_scope`: 今回追加しない機能。判断待ち・実装漏れには数えません。
- `@fault_injection`: Promise・ネットワーク・イベントなどの失敗や保留を意図的に作るケース。
- `@device`: 実際のブラウザや端末の制約を確認するケース。モックの合格を実機の確認済みと扱いません。
- `@generated`: 固定シードで再現可能な操作列を生成する補助ケース。
- `@INTRO_001` など: レビュー、実装、失敗記録を対応付けるための固定ID。

## 共通の前提と観測方法

1. 曲A・B・Cは、特記しない限り別ID・区別できる音声を持つ、30秒より長い再生可能な曲です。P・Q・Rは別IDの参加者です。準備完了は画面ラベルだけでなく対象曲IDと音源状態で確認します。
2. 「再生する」は再生ボタンなどの実際の操作から行います。サーバー状態を直接 playing にするだけではフロントの再生経路のテストになりません。API拒否や状態機械の境界テストだけは直接要求を送ります。
3. 「指定秒数だけ再生」は、実際の音声開始を基準に曲ID・開始位置・音声終了を確認します。Promiseの解決時刻やラベルだけで成功としません。次曲取得の時間を音声長に含めません。
4. 時間・反復のロジックテストでは仮想時計と制御可能な非同期完了を使い、0.1秒・1ms境界を決定的に検証します。ブラウザ統合ではメディアの再生位置と状態イベントも照合し、実機では音声出力を確認します。実機の時間許容差は計測根拠とともに明示し、100msの再生を数秒の許容差で合格にしません。
5. 「停止」は楽曲の音声出力と再生位置の進行停止を指します。早押し・正誤の効果音は楽曲と区別して観測します。無音の曲素材やホストの音量0だけを用いて、停止していない音源を見逃さないようにします。
6. 「旧処理が影響しない」は停止時点だけでなく、保留したPromise・状態通知・旧タイマーを解放した後にも確認します。旧期限の直前までしか観測しないテストにはしません。
7. 「同時」は偶然の実行順へ期待しません。テストで順序を制御し、両方の順序を確認します。サーバーが先に受理した操作を基準にします。
8. 「復旧」「再操作可能」「失敗表示」には有限の待機期限を設け、期限超過を失敗として扱います。ユーザー向けのタイムアウト値や再試行UIを新設する場合は仕様を定めます。現在のロード中表示を永遠に待つことを期待値にしません。
9. リセット直後の初期化状態と、認証済みホストによる自動 ready 遷移を区別します。瞬間的な initialization の観測だけでリセットを検証せず、曲・得点・解答者の消去と無音化を確認します。
10. 再生対象の一致、解答者は最大一人、正解ごとの加点は一回、準備・解答・結果では楽曲を流さない、過去の処理は現在のゲームへ作用しない、を複合シナリオの各操作地点で検証します。

実装では、制御コンポーネント用のSDK代替と、実MusicKit SDK＋2秒の無音テスト音源を使い分けます。上記の30秒超の実曲・区別できる音声・物理出力を満たした実機試験とは扱いません。具体的な代替範囲は [テスト環境](../harness/README.md) を参照してください。

## テストの役割

- バックエンド: 受付状態、競合時の一意性、得点、曲順、不正要求、ゲームや操作の世代をまたぐ通知。
- 再生制御: 遅延・失敗・重複・順序逆転、時計、キャンセル、同じ曲の反復。MusicKit内部の実装を複製しただけの期待値にしません。
- ブラウザ統合: UIの操作からサーバーとMusicKitまでを通す。Playwrightのルート処理を止める time.sleep 待機を使わず、既存の socket_client.sleep 経由などで処理を進めます。
- 実機: 自動再生制限、先読みの有無、タブ休止、音声出力、端末割り込み。自動化できない項目も実施記録と未確認を区別します。

件数は網羅性の保証ではありません。実装後も新しい操作や障害が見つかったら、その失敗を再現する具体的な例を追加します。
